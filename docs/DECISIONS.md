# Architecture, metrics and decisions

> Paths under `evidence/` refer to local working evidence kept by the maintainers. That directory is git-ignored and is not part of this repository.

## Architecture
Question → DeepSeek → `AnalysisRequest` JSON → `validateRequest` (whitelist) → `metrics.ts` computes → report plan (OpenUI Lang, references only) → app validates components → OpenUI renders, app fills values.
Layout: `Layout` JSON (style only) ⇄ OpenPencil `.fig` via `src/layout/mapping.ts` (ours; no built-in sync exists).

## Metric definitions (FR-18, implemented in `src/query/metrics.ts`)
Calls = records in range. Answered = outcome `connected`. Answer rate = answered ÷ calls. Conversions = records marked converted. Conversion rate = conversions ÷ **answered**. Change = current − previous answer rate, in percentage points. Unanswered = no_answer, busy, failed. Zero denominator → null → "—". Missing previous period → null → "Cannot compare".

## Fixed assumptions (human to confirm; OPEN in requirements)
Reference date 2026-11-10 (Tuesday), UTC, Monday week start. Last week = 2026-11-02..11-08; previous = 10-26..11-01. Layout saved in localStorage. Accent palette: blue, green, red, amber, purple. Call-list page size default 10.
Budget for paid calls: not provided. Ledger maximum is 0 (disabled) until set.

## Component mapping
| Component id | OpenUI | OpenPencil node | Data meaning (never edited by layout) |
|---|---|---|---|
| calls_card, answer_rate_card, conversion_card | MetricCard(componentId, metric) | `scene-<id>` frame | metric of the same name |
| daily_trend, daily_call_volume | planned | `scene-<id>` | daily series |
| campaign_table, change_ranking, call_list | planned | `scene-<id>` | per-campaign / change / drill-down query |
Editable style: order (child order), width (392 half / 800 full), accent (palette fill), pin (`locked`). Anything else is rejected.

## Spike findings (executed 2026-11-10, @open-pencil/cli 0.16.0, @openuidev/react-lang 1.1.0)
- OpenPencil CLI works headless: `import` HTML → `.fig`; `eval -w` edits via the Figma plugin API; edits persist and read back. **Node ids are reassigned after save**, so identity = node name.
- Pin has no native form; mapped to `locked`. Round-trip is one-directional per edit session (Layout → design → edits → Layout), not live two-way sync.
- OpenUI needs React ≥19 and Zod 4 (`zod/v4`). It renders library components offline and prompts from the library. Unknown components are **silently dropped, `onError` empty**.
- Not yet verified: the OpenPencil desktop/web editor GUI flow (only CLI/headless), DeepSeek output quality against the OpenUI prompt.

## Phase 2 decisions
- Browser calls `/api/plan` on the Vite dev server; the server holds the key, reserves budget, calls DeepSeek and returns a validated `PlanOutcome`. `SCENE_MODEL_MODE=stub-fail|stub-invalid` injects failures for offline tests. There is deliberately no stub that returns a successful "live" plan.
- Browser-reachable code must not import Node modules (`tests/browser-safe.test.ts`). Found when the first browser run showed a blank page because the UI imported `planner.ts` → `budget.ts` → `node:fs`; prepared analyses now live in `src/ai/prepared.ts`.
- The OpenUI program is built by the app from validated component ids (`programFor`); `unknownComponents` blocks anything else before rendering. Values are read from a React context (`EnvContext`), never from model text.
- A follow-up that only names components and the same intent extends the current report; otherwise it replaces it. Date/campaign filters belong to the user and survive follow-ups.
- Prompt gets `Selected campaign: <id|none>` from the app (live smoke test 1 failed on "expand this campaign" without it).

## Phase 3 decisions
- **Pinned area.** Pinned components form a fixed area at the top (layout order) and stay in the report whatever the latest question asked for. Other components follow in layout order. Implemented in `src/layout/arrange.ts`.
- **Pin conflict.** A newly added component that layout order would place before a pinned one is a conflict: the pin wins, the new component goes below, and the user is offered "Unpin" (FR-27). Defined by `pinConflicts`.
- **Edit view and OpenPencil.** The edit view is a separate page (`#/edit-layout`). Apply writes the draft to `.scene-data/design.fig`, reads it back with OpenPencil and runs `mapNodesToLayout`; only the mapped result goes live. "Write design file / Import edits from file" lets a design edited in OpenPencil re-enter as a draft (applied only on Apply). Layout JSON is validated again by `parseLayout` at every untrusted boundary (storage, request bodies).
- **Persistence.** `localStorage` key `scene.layout.v1`; corrupt, partial or unavailable storage falls back to the default layout, and a save failure is shown to the user.
- **Drill state** (outcome, sort, page) lives in the report spec; the date range and campaign filters stay user-owned. "Clear filters" resets both. Page size 10.
- Not covered by any browser test: pinned-area anchoring when the pinned component is not already first in layout order (covered only by the unit test in `layout-logic.test.ts`; confirmed by a mutation check).

## Phase 4 decisions
- Layout apply uses a per-request temp design file; only export/import use the shared `.scene-data/design.fig`. A shared file raced under parallel browser tests (old version failed 3 of 4 parallel runs; fixed 4 of 4). Browser tests run serially because export/import tests share that file.
- A "How this report was made" panel shows the validated request the model (or a prepared analysis) chose and what the application did, to make model vs template contribution visible (NFR-2).

## v0.2.0 decisions (chat-centric)
- **State ownership.** A report is a value inside its Agent message (`src/chat/state.ts` `ReportInstance`): spec (incl. drill sort/page), current filters, `askedFilters`, own layout, open call, editing flag, source. There is no global report. Pure helpers (`reportFromRequest`, `drillReport`, `patchReport`) return new messages; tests assert earlier messages are the same objects after a later query.
- **Scope inheritance.** A new plan takes range/campaigns from the request, else from the latest report, else defaults. A drill action copies the source report's range (frozen at click time). A component-only follow-up of the same intent becomes a NEW report that carries the previous components forward.
- **Narrative text** (`src/chat/narrative.ts`) is computed by the app from engine data; the model still only chooses a validated request. Small samples (<30 calls in a period) are flagged in the change text. Note: by hand-computed data the biggest drop is Tiny Sample Test (-50.0 pp, 10 calls); Payment Reminder (-20.0 pp, 300 calls) is the biggest by volume, so every ranking row has its own "View unanswered calls" button besides the primary action.
- **Per-report filters** (range, campaigns) edit only that message; a "filters changed after the question" badge shows divergence and "Reset to original scope" restores `askedFilters`.
- **Layout.** Each report copies the layout preference at creation. "Edit layout" opens the existing form + OpenPencil round trip as a modal; "Apply to this report" changes that report only; "Apply and save as preference" / "Save layout as preference" update the localStorage preference (and log an action message). Existing reports never change when the preference changes.
- **Pins** now mean "placed first within a report that contains the component". They no longer force the component into later replies, so `pinConflicts` and the conflict banner were removed.
- **Sources.** `live` | `fallback` | `action` (UI click, "Direct action · no model call"). Direct actions are never labelled live.
- Failures (model error, unknown metric, ambiguous campaign) are Agent messages; the error message disappears when a prepared analysis or retry succeeds, reports are untouched.

## v0.2.0 follow-ups (ranking, metric-only, scope, sample size)
- **Request schema** gained `sortBy` (calls, answered, answer_rate, conversions, conversion_rate, unanswered_calls), `order` (default desc), `limit` (1-7) and `only`. Orphan `order`/`limit` without `sortBy` is rejected. The app ranks (`rankRows`, nulls last, ties by call volume then id); the model never supplies figures.
- **Components from the request.** A ranking yields the ranked table only (cards/trend would show totals over ALL campaigns and mislead). Named `metrics` narrow the cards; with `only` nothing else is added, without it the default trend and table follow.
- **Scope.** A new question covers ALL campaigns unless it names some; the date range follows the conversation. A component-only follow-up of the same intent modifies the previous report, so it keeps that report's campaign scope. (Bug found by the user: "top 3" inherited a narrowed Spring Renewal scope.)
- **Sample size.** `MIN_SAMPLE = 30` calls (assumption, human to confirm). The change-analysis conclusion and primary drill action use the biggest drop among campaigns with >= 30 calls in BOTH periods; larger drops on smaller samples stay in the table with a "low sample" badge and are named in the text. On the demo data the conclusion is Payment Reminder (-20.0 pp), not Tiny Sample Test (-50.0 pp, 10 calls).
- Live check (3 requests): "top 3 campaign of answer rate", "only conversion rate", "2 lowest answer rate last week" all produced the expected requests.

## v0.2.0 free composition
- `only: true` + `components` (and/or metric cards) = EXACTLY those components, any intent; without `only`, components are added to the intent's default set. Report is flagged `custom` and titled "Custom report".
- `call_list` is allowed in any composition but needs exactly one campaign (`campaignIds`), otherwise the planner returns `need_campaign`; the campaign becomes the report's drill target and the report's other components keep the all-campaign scope.
- Narrative and basis text follow the components present (call_list > change_ranking > ranking > cards-only > overview), not the intent. `tests/library.test.tsx` renders all 255 non-empty subsets.
- Still one shared scope (range + campaigns) per report; per-component scopes and new chart types are NOT supported.

## Regression note (planner)
Adding `sortBy` made the live model answer "biggest answer-rate drop" with `sortBy: answer_rate_change`, rejected as `bad_sort`; found by the user, not by my checks (I had only live-tested the new phrasings). Fix: prompt says change questions are change_analysis without sortBy, and `normalize()` drops a redundant sortBy/order/limit for change_analysis/drilldown (or maps `answer_rate_change` to change_analysis). Other invalid sorts stay rejected. Rule: after any prompt/schema change, re-run the full demo question list against the live model (all 10 passed on 2026-11-10).


## v0.3.0 decisions (Retail mode)
- **Additive switch.** `src/Shell.tsx` wraps `App` and `RetailApp`; both stay mounted once opened (hidden), so switching loses nothing. Retail mounts on first visit, so existing browser tests never see retail DOM. Retail test ids all start with `rt-`. The only edits to existing files: `main.tsx` (renders Shell), `.app` height in CSS, an optional `SCENE_PORT` in vite/playwright config, and a `retailApi` plugin.
- **Fixed reference date** 2026-11-10 (same as Reporting). Latest-receive date must be after today and not after the departure date; both are asked for separately.
- **Policy (synthetic, in `src/retail/data.ts` / `rules.ts`).** Exchange: in warranty + stock; ships next day, transit 4/5/8 days by zone (urban/suburb/remote), shipping 0/10/25. Repair: always possible; in warranty free incl. return shipping, out of warranty 129.00 + zone shipping; pickup+1 day arrival, 5 days processing, return transit 2/3/5. Refund: in warranty only, 5% per full month of use (max 40%) deducted, pickup+1, 3 inspection, 3 payout days. Zones come from map distance to the centre (≤20 urban, ≤35 suburb). Pickup window tomorrow..+7; a slot is full when (day + slot index) % 5 == 0; remote pickup addresses have no courier pickup. Every number is hand-computed in `tests/retail-rules.test.ts`.
- **Late is "after the deadline".** Arriving ON the latest-receive date counts as on time (margin 0).
- **Quote versions are keys, not counters.** `plansKey` (order, symptoms, all three quotes) and `confirmKey` (whole payload) are compared to a card's frozen snapshot to decide if it is still actionable. Local edits inside a card that change the quote (address, pickup date/slot) therefore make earlier cards "Updated" without special cases.
- **Recalculation is explicit.** Any key change shows "Recalculating…" (300 ms simulated lookup) and disables next/submit until done.
- **Natural language.** `/api/retail/interpret` asks DeepSeek for an `Intent` (whitelist, strict validation). On any failure (including budget refusal, offline tests) the client falls back to `parseIntentLocal` and labels the message "Understood by rules (model unavailable, no model call)". There is no fake "live" result. Quick replies are direct actions ("Quick action") and go through the same `applyIntent`.
- **Submit service.** Server re-validates: shape, explicit `confirmed`, eligibility, readiness, quote fingerprint. Idempotent per key and per identical payload inside one session (first version deduplicated across sessions; a browser test caught it masking the failure scenario for a different "customer"). Failure scenario fails the first attempt per key with no case created.
- **Pickup vs delivery.** `pickupAddr` and `delivery` are separate; "ship to my company" only calls `setDelivery`. With the refund plan selected it asks what is meant and changes nothing.
- **Not done:** OpenUI/OpenPencil for retail cards; live-model run; real map tiles.

- **Language.** The requirement document is Chinese but the UI is English like Reporting (user decision after the first build used Chinese). All Retail UI text, rule explanations, demo data and service messages are English; dates read like `Nov 15`. `parseIntentLocal` is English-first and still accepts a few Chinese phrases as input.

## v0.3.1 decisions (conversational Retail flow)
Trigger: user review of v0.3.0 found (1) a big form collecting item, fault, description and dates at once, and (2) "I would like to drop-off, give me the address" ignored (no such intent; reply told the user to use the cards). Root cause: `applyIntent` was a step machine that fell back to one intake card, and the intent model had no return method / service point concept.
- **Driven by what is missing.** `nextNeed(task)` returns the single next thing to ask (order → symptoms → deadline → plan → return method → place → service point / drop date or courier date+slot → confirm). Each turn: merge what the user said (any order, several facts per sentence), then ask only that. `applyIntent` is pure; `tests/retail-dialog.test.ts` replays whole conversations without React.
- **New intent fields** (all whitelisted): `orderId` (must be a known order; resolved from "the first one" / "the Lite" against what was SHOWN), `returnMethod`, `locationPref`, `servicePointId`, `pickupDate`, `wantsAddress`, `askQuestion`. The model gets a context block (orders and service points as shown, what the agent is waiting for, what is known) so references resolve. A drop-off wish stated early is stored and used when the return step comes. "Ship it to my company" (delivery of the NEW item) and "near my company" (where to look for service points) are different fields.
- **Rules fallback is a peer, not an afterthought.** It uses the same context (`ParseContext.expect`): ordinals only apply while an order question is open; a bare date answers the open date question. If the model returns an empty intent the app uses the rules result and labels it "the model returned nothing usable". Verified on the same 10 phrases (10/10 each).
- **Small cards, then summaries.** Each card answers one need; `markAnswered` collapses answered cards (by typing or clicking) into a summary line with "Change" (which just asks again; everything else is kept). Cards never duplicate an open question. A plan comparison whose numbers changed collapses to one "Earlier comparison … Updated" line. The address card stays open through its own answers and the agent's follow-up, and collapses when the user does something else.
- **Forms only when structured data is missing:** the address form appears only when no company address is saved (or the user asks to change it); pickup address defaults to the saved home address and is not editable in chat (gap).
- **Not understood** → `clarify(need)`: restates the pending question in context, with quick replies where the answer is a choice; never a generic "use the cards" message.
- **Drop-off.** Service points carry address, hours and an appointment flag; the list is filtered to points that handle the chosen plan, sorted by distance from the company or home address. If a plan has no drop-off point the app says so and uses a courier. A drop-off date is still required (it feeds repair/refund estimates).
- **Bugs found by the browser tests, not by unit tests:** the confirm card was created without a submit key (every submit refused, correctly creating nothing); the address card collapsed in the same turn that created it; plan words after a question mark were ignored ("Repair is fine. Where can I drop it off?"); "Fastest first" was read as "the first order". Fixed, each covered by a test.

## v0.3.1 follow-up (user review of a real session)
- **Which actions call the model.** Only typed sentences (and the example-sentence button) call `/api/retail/interpret`. Quick replies, radio choices, date pickers and "Change" links are direct actions with explicit intents: deterministic, free, and labelled "Quick action" under the bubble. R3 asserts exactly one interpret request for a whole component-only journey. A user who clicks through will therefore see few or no model calls; this is by design (the model is for free text, not for buttons).
- **Old plan lists no longer say "Submitted".** The badge on a superseded comparison claimed "Submitted" when it was only closed (and showed whenever the chat had been submitted later). Now: the latest answered comparison reads as the chosen plan with today's numbers ("Plan: Repair · estimated delivery Nov 22"); a question asked again keeps only its newest card (older answered copies are hidden); an unanswered comparison whose numbers moved shows "Earlier comparison … Updated"; only the confirmation card that was submitted says "Submitted". Bug behind it: a later pickup date refines the repair/refund estimate, which changed `plansKey` and pushed the chosen plan's card into the "earlier comparison" line.

## v0.3.2 decisions (traceable natural language, no silent substitution)
Review request: trace every natural-language send end to end; the model reads typed messages together with the task state by default; buttons execute directly; rules must not silently replace the model; "Understood by model" must never appear without a real call.
- **Policy change.** Superseded: "if the model fails, fall back to rules" (v0.3.0/v0.3.1) and "if the model returns nothing, use rules". Now: typed message → model (with `contextFor(task)`). A model failure shows "Model call failed, nothing was understood", changes nothing, and offers **Retry with the model** or **Use basic rules for this message** (an explicit click, labelled "Understood by rules (you chose rules after the model failed)"). A valid but empty model answer is a real model result ("nothing actionable") and goes to the contextual clarification. Rules otherwise run only when the user selects **Rules only (no model calls)** in the header (visible, per session, labelled on every bubble). Buttons, choices, date pickers and "Change" are direct actions ("Quick action (direct, no model)") and never touch `/api/retail/interpret`.
- **Trace model** (`src/retail/trace.ts`). Browser creates a request id (`rq-<time>-<rand>`), sends it as `x-request-id` and in the body; the server validates or generates one, echoes it, and returns a `ServerTrace` with every answer. `deepseekComplete` got an optional observer (`trace`, `reserveFn`) emitting `no_key | reserve_refused | reserved | sent | response(first byte) | done | transport_error`; Reporting passes none and is unchanged. **`modelCalled` is true only when the `sent` event happened**: no key and budget refusal are `false`; provider errors (HTTP 503), timeouts and invalid model output are `true` with the failure named. Timings: `ttfbMs` (first byte), `modelMs` (whole response), `totalMs` (server), and the browser's round trip. (A first version reported only first-byte time, which made server time look 5-10x the model time; the live run exposed it.)
- **Never trust the happy path.** `checkResponse` rejects a success answer whose trace is missing, belongs to another request id, or has `modelCalled !== true`; `viaLabel` returns "model" only from the server's proof. Both are unit-tested and browser-tested with mocked server answers (R18, R19).
- **Server stubs no longer pretend.** `stub-fail` / `stub-invalid` answer "failed: model disabled (offline test mode), no request was sent" with `modelCalled: false` (they used to throw a fake `http_503`). Offline browser tests pick **Rules only** explicitly.
- **Where it is recorded.** Per user bubble (`rq-… · model called (deepseek-chat, HTTP 200) · model 1049 ms (first byte 243 ms) · server 1051 ms · round trip 1056 ms`), in the header **Trace (n)** panel (including rules-only and retried turns, `retry of <id>`), in server memory (`GET /api/retail/trace[?requestId=]`), in `.scene-data/retail-trace.jsonl` (git-ignored) and in the dev-server log. Records hold ids, mode, lengths, call status, HTTP status, budget reservation number, outcome, failure, intent KEYS and timings. They never hold the API key, the prompt, the user's message text or the model's reply.

## v0.4.0 decisions (the model plans the turn; the application owns the facts)
Trigger: with live traces the model was called every turn, but "Why is exchange better for my trip than repair?" came back as `askQuestion` and the UI said "Of course, ask away". Labelling messages into fixed intents caps the agent at the flow's own steps.
- **Turn plan instead of intent labels** (`src/retail/turn.ts`). One JSON plan: `mode` (discuss | what_if | change), `changes` (the old Intent keys, change only), `queries`, `answer`, `ui`, `quick`. `/api/retail/interpret` keeps its URL and trace but now runs `runTurn`: call 1 plans; if the model declared queries the app runs them and call 2 composes the final wording from the results. There is no "execute" mode: submission stays a button.
- **Facts bundle, not phrase branches.** Every turn the model gets STATE, PENDING (what the user is looking at: orders/service points in the order shown, what the agent waits for) and FACTS computed by the application for ANY question: current plans, plans for every saved delivery address with deltas, every service point with distances, policy. What-ifs outside that grid go through the generic tools. Nothing is keyed on a sentence.
- **Fact guard** (`guardAnswer`). Money, month-day dates, "N days" and "N km" in the answer must be in the facts, the query results, or the user's own message; otherwise the wording is replaced by `fallbackAnswer` (generic renderer over the same data), the trace says "wording replaced by guard", and the UI notes it. The guard found a bug of mine in the live run: `margin 0` was read as the date "Mar 0" (regex allowed any letters after `mar`); month names are now whole words in the guard and the rule parser. It cannot check meaning, only figures (see gaps).
- **Safety of the three modes.** discuss/what_if: `changes` discarded and flagged (`ignoredChanges`), no state touched (unit + browser tests compare the whole state before/after). change: through `applyIntent`, then a generic `diffTask` report. Suggested buttons that apply something carry validated `changes` and, like the compare card's "Apply this change" (intent derived from the tool's overrides, not from model text), run with the same diff report.
- **Contract lessons from the real model** (each caught by a live run, then covered by a test): the facts did not list the orders on screen so "the first one" could not resolve; the model asked for missing information itself instead of leaving that to the app (contract now forbids it); it could not name valid values (the enums are now spelled out) and mixed address ids into `deliveryTarget` (equivalent spellings are normalised: saved address id, case, "House"/"Office", symptom wording); it refused to do date arithmetic and had no tool for it (`deadlineShiftDays`). An invalid optional suggestion no longer sinks a good answer (dropped and counted); state-changing `changes` stay strict.
- **Order of messages.** "Changed: … Unchanged: …" now comes before the follow-up question.
- **Appointment points.** `ServicePoint.appointment` was only a label; now a booked slot is required (`readiness`, `nextNeed`, drop-off card with slots, confirm/receipt show "Appointment booked"). `QuoteInput.method` makes step labels truthful for drop-off ("you drop off the old unit").
- **Budget.** The ledger cap was raised 200 → 400 by the user in chat ("add another 200 to the allowance"); recorded requests are untouched. This iteration spent 84 requests (55 scripted verification, 29 in the real-browser spec), more than planned: two attempts failed on a network error but were already reserved, one browser run was started by mistake, and several prompt/contract fixes needed re-runs.


## v0.5.0 decisions (the model writes the interface; the application owns facts, state and submission)
Source: `docs/requirement/scene-v0.5-openui-proposal-20261111.md`. Reporting is unchanged.
- **Two model calls per typed turn, one per pressed control.** Call 1 (JSON) plans: mode (discuss | what_if | change), changes, read-only queries. Call 2 (free text) writes OpenUI Lang. A control the user pressed is already applied by the application, so only the Lang call is needed. At most ONE repair call, only when validation fails; it is reserved, traced and counted like any other. Nothing else is retried.
- **Lang channel is separate from JSON** (`deepseekLang` = `deepseekComplete({json:false})`): no `response_format`, same `reserve()` before every request, same per-call events. The system prompt is generated from the library (`library.prompt`, tools/bindings sections off) plus application rules; the spec is saved in `evidence/v0.5.0-20261111/library-spec.json`.
- **Bindings, not figures.** `buildBundle` creates ids (`quote.q1.alt.exchange`, `cmp.q1`, `sp.sp-2`, `addr.home-1`, `order.<id>`, `method.store` ...). A component accepts only the kinds that fit its meaning, so a total cannot appear as a date. Wording may contain a figure only if it is in the facts/results/user message (`guardAnswer`, now applied to every Text, Notice and label). Free text still can be wrong in meaning; only figures are checked.
- **Validation before rendering** (`checkLang`): the parser does not enforce array sizes or string lengths and the renderer silently drops unknown components, so both are checked here. Constructors are looked for outside string literals (first live run: "Home (Urban)" in a Text was misread as a component and rejected 7 good programs; fixed, tested, and the first run kept in the evidence as it was).
- **The program must offer what the application is waiting for** (change turns): `requiredControls(need)` maps the pending need to controls, and only what is actually missing (a known date is not asked again; a walk-in point asks no slot). On discuss/what_if turns the prompt forbids adding the pending question (live: 6 of 6 explanation/what-if answers did it before the rule, 1 of 6 after).
- **Semantic events** (`events.ts`): select / multi / date / slot / form / adopt / apply / ask. The app checks the message revision, that the control was in the validated program, and that the value is legal; then the same `Intent` goes through `applyIntent` as typed language. `adopt` takes the change from the tool result (`applyIntent` of the comparison), never from model words; `apply` has no date fields.
- **Frozen messages.** A Lang message stores the validated program, the bundle (facts) and the task snapshot. Controls are live only while `revisionOf(task)` equals the message revision and nothing is submitted/in flight; stale messages keep their facts and show "out of date".
- **Draft vs business state.** DatePicker/TimeSlotPicker inside a Form only fill a message-level draft; the Form button is one explicit event. Map pin click only highlights. The task changes only through `applyIntent`.
- **Submission stays application-owned.** Confirmation and receipt are the existing app cards; no component or Lang statement can submit. Server re-validation and idempotency are unchanged.
- **Business contract fixes (A).** `pickupSlot` added to Intent, parser, model contract and `applyIntent`; opening hours constrain appointments (`slotWithinHours`, `appointmentSlots`, `appointmentProblem`); `marginText` replaces "before"/"to spare" wording (0 days = "on your deadline day").
- **`noAsk`.** `applyIntent(..., {noAsk:true})` records and reports a change but does not ask the next question; in the model-written interface the model composes that UI. The server applies the same pure function to show the model the state the user will see.
- **Contract lesson from the real model.** The v0.4 planning prompt did not list `pickupSlot`, so "between 2 and 6 in the afternoon" lost its time window (live cases 8-9 caught it; fixed and re-run).
- **Budget.** Cap unchanged (400, set by the user). The ledger read 269 at the start of this iteration (264 was the last figure quoted); this iteration used 84 requests (see the report).
