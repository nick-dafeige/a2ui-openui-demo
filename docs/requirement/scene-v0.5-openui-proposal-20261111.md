# Scene v0.5: proposal for a native OpenUI Retail

Status: read-only exploration and design. No project files were changed, no new experiments were run and no paid model was called.

## Basis and current state
Official docs: https://www.openui.com/docs/openui-lang/defining-components , https://www.openui.com/docs/openui-lang/interactivity , https://www.openui.com/docs/openui-lang/architecture
Locally installed `@openuidev/react-lang` 1.1.0. Its declarations include Renderer, onAction, isStreaming, initialState, onStateUpdate, toolProvider, useStateField, createParser and generateSystemPrompt. An interface being present does not mean an end-to-end integration has been verified.
Retail `runTurn` currently outputs a JSON TurnPlan: mode, changes, queries, answer, ui, quick. `ui` allows at most 3 cards, which RetailApp then renders through conditional branches. The application also adds a compare card for query results. The model does not control how a card is composed inside. The shared `deepseekComplete` forces `response_format=json_object` and reads the full response without streaming, so it cannot be used directly for a Lang stream. Reporting has a real Renderer, but its Lang is generated by `programFor`.

## Goal
From the same business state, generate in-chat UI with a different structure for different questions. Allow plain-text answers. Language, choices and forms all produce the same business events. The model orchestrates the presentation; the application owns the business truth and the right to submit.

## First slice
Keep the business planning and deterministic queries; change the second stage so the model writes OpenUI Lang. The first complete path is: explain why exchange rather than repair, then a hypothetical comparison for the home address, then adopt it, then an explicit appointment time slot. The design target is at most two model calls per natural-language turn, with no fixed third call. When no query is needed, one composition call from verified facts may be used; any optimisation must be decided by actual evidence.

Step one verifies the minimal library, Lang generation, Renderer, action and message state on their own, without upgrading the whole dependency tree and without affecting Reporting.

## Components
Layout: Stack, Section, Columns (stacking on a narrow screen).
Content: Text, Notice, OrderSummary, WarrantyStatus, QuoteMetric, QuoteComparison, AddressSummary, ServicePointSummary.
Input: SingleChoice, MultiChoice, QuickReply, Form, DatePicker, TimeSlotPicker, Map.
Key fact components reference a bindingId or data path generated by the application; they do not accept a fee, eligibility or estimated delivery time typed freely by the model. Wrapping the old whole-page templates such as PlansCard or ConfirmCard and then claiming dynamic composition is not allowed. The high-risk final confirmation and receipt may use dedicated application-owned components.

## Data and state
EvidenceBundle carries taskId, stateRevision and quoteRevision. A generated interface may reference only the permitted data bindings, and the data path must match the display meaning. Draft form state belongs to the message's Renderer; business state belongs to the TaskStore. Input changes the draft; an explicit choice or apply goes through validation before it writes business state. A hypothetical query never writes the official state.
A message stores the program, the library version, a frozen snapshot of the facts, the form state, the action permissions and the task revision. Historical facts are not silently updated, and stale actions are disabled. The model cannot get a pass for a "correct number" from arbitrary numbers in the history.

## Events
onAction → a validated semantic event → check of current permission and version → business reducer or tool → UI state or a new agent turn.
Field drafts, paging and map marker selection normally do not call the model. Actions that need an explanation or re-planning go to the agent. Final submit is authorised only by an explicit button; it must not be a Query or Mutation that runs automatically when the interface is generated. The server re-validates, is idempotent, and returns the receipt.
Unify the state fields pickupSlot, date, order, address and so on with the natural-language contract, and fix the current problem that the time slot is ignored. A store appointment is separate from a courier pickup slot, and opening hours are validated.

## Rendering and reliability
Add a dedicated provider channel for Lang (keeping reserve and trace); the client configuration that forces JSON cannot be reused. Generate the prompt from the library spec, and keep the business-planning JSON. Validate the complete program before any interaction, and introduce a streaming preview afterwards: controls inside the stream cannot be submitted, and unlock only after validation completes. Check components, props, data references, actions, structure limits and stale revisions; do not rely on the Renderer silently dropping unknown components. On failure, keep the last valid message and state the failure and any fallback the user chose explicitly; if a repair request is used, it must be limited and counted against the budget.

## Implementation order
A. Business contract: pickupSlot, opening-hours constraints, wording for a time equal to the deadline, message and data revision numbers.
B. Minimal OpenUI vertical slice: components and prompt generation, real Lang generation, chat rendering, action flow back, back-end fact bindings.
C. Cover item confirmation, fault, deadline, plan, address and map, and store appointment with composed components; add streaming and persistence.
D. After acceptance, migrate Reporting to model-written Lang. OpenPencil is used this round for visual component templates and does not claim a Retail round-trip; lossless two-way editing from an arbitrary generated tree to a design file is a separate scope.

## Acceptance
1. With the same state, asking for a reason may give text only or the key figures; asking about service points gives a map plus a selectable list; when only the date is missing, only a date appears; a multi-constraint comparison gives a comparison plus local filtering. No branch from a predefined question to a whole-card template.
2. One message combines a map, a service-point choice and a date; it traces back to the model's raw Lang and the application's validation record.
3. Compare first without modifying; an explicit adoption modifies only the corresponding fields; natural language and components produce equivalent business state for the same information.
4. Stating a specific date and time slot needs no repeated clicks; every time slot is inside the store's opening hours.
5. Changing the address refreshes the quote and invalidates the old confirmation; historical snapshots are kept; nothing can be submitted inside the stream; repeated submit is idempotent.
6. Components outside the library, wrong fact references and illegal actions are blocked and cause no business side effect.
7. A limited frozen protocol verifies wordings not used in the prompt examples, including at least one set in Chinese, recording render success, correct facts, correct interaction and appropriate task separately; passing unit tests cannot stand in for user utility.
8. Zero-cost fixtures and browser tests first, then a small live batch within the ledger's actual allowance; the budget is reserved per request, failures and repairs both count, and the cap is not changed. The current exploration starts no live run.

## Deliverables and uncertainty
Deliver the model's raw Lang, the library spec and version, the binding snapshots, parse and validation results, action and state diffs, failures, screenshots and call counts. No keys may enter the evidence. Only after the first slice passes do the remaining templates get extended. Unknown: how well DeepSeek follows a library of this size and the Lang format, the latency to a first usable result, whether the expressive freedom improves task completion, and the mapping cost OpenPencil editing needs. All of these need real execution or user testing, and none has been verified so far.
